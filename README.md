# HustleHub+ --- Secure Freelance Marketplace

HustleHub+ is a secure MERN freelance marketplace. Freelancers advertise
services ("gigs"), clients browse and book them, each booking creates a
transaction record, and freelancers can view income generated by
completed bookings.

## 1. System overview

HustleHub+ is a full-stack freelance marketplace that allows freelancers
to advertise their services and clients to browse, book and pay for
those services using a simulated payment process. The system records
transactions generated by bookings and provides freelancers with an
income summary and an estimated tax calculation based on qualifying
transaction data.

The application uses a React frontend, a Node.js and Express REST API,
and MongoDB for persistent storage. The backend is the main security
boundary: the frontend does not communicate directly with the database.
Authentication, authorisation, validation, sanitisation and business
rules are enforced by the backend before protected operations are
completed (Express.js, n.d.; Joi, n.d.; MongoDB, n.d.).

Part 2 extends the original registration and login functionality into a
full-stack application with:

-   MongoDB persistence through Mongoose.
-   Gig creation, browsing, updating and deletion.
-   Client bookings and simulated payments with transaction records.
-   Role-based access for clients, freelancers and administrators.
-   Freelancer income summaries and backend tax estimation.
-   Input validation and sanitisation, rate limiting, security headers
    and HTTPS/TLS.
-   Automated API tests using Postman/Newman and frontend tests using
    Vitest and React Testing Library.

**Booking flow.** A client selects a gig and confirms a simulated
payment. The application creates a booking and a linked transaction
record. No real payment is taken.

**Income tracking.** Freelancer income is derived from completed
transactions associated with the freelancer. Booking records preserve
the gig title and price at the time of booking, so later changes to a
gig do not rewrite historical booking information.

**Tax estimation.** The backend income functionality includes a tax
estimate based on the current South African tax year and the income data
used by the calculation. The estimate is informational and is not
professional tax advice. The current freelancer dashboard does not
display a dedicated tax card or tax chart.

## 3. System architecture

HustleHub+ follows a three-tier MERN architecture:

1.  **Presentation layer:** React frontend running in the browser.
2.  **Application layer:** Node.js and Express REST API containing
    authentication, authorisation, validation and business logic.
3.  **Data layer:** MongoDB database accessed by the backend through
    Mongoose.

The frontend communicates with the backend through REST API requests
over HTTPS/TLS. Database operations are performed by the backend after
the relevant security checks.

``` mermaid
flowchart TB
    U[Client or Freelancer] --> FE[React Frontend]
    FE -->|HTTPS / REST API| API[Node.js and Express API]
    subgraph Security[Backend security controls]
      AUTH[JWT Authentication]
      RBAC[Role and ownership checks]
      VALID[Joi Validation and XSS Sanitisation]
      LIMIT[API, Authentication and Booking Rate Limits]
      HEADERS[Helmet Security Headers]
    end
    API --> AUTH
    API --> RBAC
    API --> VALID
    API --> LIMIT
    API --> HEADERS
    API --> LOGIC[Application Controllers and Business Logic]
    LOGIC --> DB[(MongoDB)]
```

For a protected operation, the backend verifies the JWT, checks the
user's role and resource ownership where applicable, validates and
sanitises input, and then performs the database operation. Requests that
fail a security check receive an appropriate HTTP error response.

## 6. Data model

The application stores users, gigs, bookings and transactions in
MongoDB.

``` mermaid

    USER ||--o{ GIG : owns
    USER ||--o{ BOOKING : makes
    USER ||--o{ BOOKING : receives
    GIG ||--o{ BOOKING : booked
    BOOKING ||--o| TRANSACTION : generates

    USER {
        string email
        string password
        string role
    }
    GIG {
        string title
        string description
        string category
        number price
        ObjectId freelancer
    }
    BOOKING {
        ObjectId gig
        ObjectId client
        ObjectId freelancer
        string gigTitle
        number amount
        string status
    }
    TRANSACTION {
        ObjectId booking
        number amount
        string currency
        string paymentMethod
        string status
        string reference
    }
```

Important data-handling decisions include:

-   **Price snapshots:** the booking stores the gig title and price at
    the time of booking.
-   **Transaction linkage:** a transaction is linked to its booking.
-   **Password protection:** password hashes are not returned in
    ordinary user responses.
-   **User scoping:** income, booking and transaction queries are scoped
    to the authenticated user where required.

## 8. Security implementation

### 8.1 Password hashing

The backend uses bcrypt to hash passwords before storage and to compare
a supplied password with the stored hash during login. Passwords are not
stored as plaintext. The validation middleware enforces a minimum
password length and complexity requirements, and applies a maximum of 72
UTF-8 bytes to accommodate bcrypt's input limit.

Password fields are deliberately excluded from XSS sanitisation so that
a password is processed exactly as entered.

### 8.2 JWT authentication

The authentication middleware expects a bearer token in the
`Authorization` header. It verifies the token using `JWT_SECRET`,
attaches the decoded claims to `req.user`, and allows the request to
continue only when verification succeeds. Missing tokens and invalid or
expired tokens return HTTP 401.

### 8.3 Authorisation and role-based access control

The role middleware checks the authenticated user's role against the
roles allowed for a route. If the user is missing or does not have an
allowed role, the API returns HTTP 403.

Registration validation allows only the `client` and `freelancer` roles.
Administrative accounts are created through the seed script rather than
public registration.

Resource ownership checks are also required for operations involving a
user's own gigs, bookings and financial records. These checks are
enforced by the relevant route/controller logic, not by frontend
navigation alone.

### 8.4 Input validation and sanitisation

The validation middleware uses Joi schemas to check request bodies. It
sanitises string values with the `xss` package before validation, except
for password fields. It also uses `stripUnknown: true` so that fields
not included in the schema are removed.

The supplied validation code defines schemas for registration, login,
gig creation, gig updates and booking creation. It also validates
MongoDB-style object IDs as 24-character hexadecimal strings.

These controls help reject malformed input, HTML/script payloads,
unexpected object values and unapproved fields.

### 8.5 Rate limiting

The backend defines three rate limiters in `middleware/rateLimiters.js`.
Each uses a 15-minute window. The defaults can be overridden through
environment variables.

  ------------------------------------------------------------------------
  Limiter                              Default limit Behaviour
  --------------------- ---------------------------- ---------------------
  General API            300 requests per 15 minutes Helps reduce
                                                     excessive API traffic

  Authentication           10 failed attempts per 15 Successful requests
                                             minutes are skipped by the
                                                     limiter configuration

  Booking                 20 requests per 15 minutes Limits repeated
                           per authenticated user ID booking requests by
                                                     an account
  ------------------------------------------------------------------------

The configuration enables standard rate-limit headers and disables
legacy headers. Exceeding a configured limit returns HTTP 429 with a
JSON error message. The rate-limit test collection verified the booking
and authentication limiters, including the `Retry-After` header.

### 8.6 Security headers

The project uses Helmet to configure HTTP security headers. The Newman
API collection checked headers including Content-Security-Policy,
X-Content-Type-Options, X-Frame-Options and Strict-Transport-Security,
and checked that the `X-Powered-By` header was not exposed.

### 8.7 HTTPS / TLS

The local backend is configured to use HTTPS with certificate files in
the backend `ssl` folder. The local certificate is self-signed, so a
browser or API client may require certificate verification to be handled
during local development. A trusted certificate should be used for a
production deployment.

### 8.8 Environment variables and error handling

Configuration values such as the MongoDB connection string, JWT secret
and admin credentials are stored in environment variables. The `.env`
file must not be committed to the repository.

The backend uses centralised error handling to return controlled
responses. Detailed internal errors should not be exposed to API
clients.

## 10. Running the application

### 10.1 Prerequisites

-   Node.js 20 or later and npm.
-   A MongoDB Atlas cluster or a local MongoDB server.
-   Git.
-   Postman is optional because Newman is included in the backend
    dependencies.

For MongoDB Atlas, add the development machine's IP address under
Network Access and ensure the database user has the required
permissions.

### 10.2 Backend setup

From the repository root:

``` bash
cd hustlehub-backend
npm install
```

Create `hustlehub-backend/.env` with the relevant values:

``` text
PORT=5000
CLIENT_ORIGIN=http://localhost:5173
MONGO_URI=<your-mongodb-connection-string>
JWT_SECRET=<your-long-random-secret>
ADMIN_EMAIL=<your-admin-email>
ADMIN_PASSWORD=<your-strong-admin-password>
API_RATE_LIMIT=300
AUTH_RATE_LIMIT=10
BOOKING_RATE_LIMIT=20
```

Do not use the example placeholders literally. Supply your own local
configuration and do not commit `.env`.

Generate a random JWT secret with:

``` bash
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

Create or confirm the admin account:

``` bash
npm run seed:admin
```

Start the backend:

``` bash
npm run dev
```

Wait for the MongoDB connection and HTTPS server startup messages. The
backend is expected to run at:

``` text
https://localhost:5000
```

Because the development certificate is self-signed, open the backend
address in a browser and accept the local certificate warning if
required. Do not use this development certificate as a production
certificate.

### 10.3 Frontend setup

Open a second terminal from the repository root:

``` bash
cd hustlehub-frontend
npm install
```

Create `hustlehub-frontend/.env`:

``` text
VITE_API_URL=https://localhost:5000/api
```

Start the frontend:

``` bash
npm run dev
```

The Vite development server normally runs at:

``` text
http://localhost:5173
```
